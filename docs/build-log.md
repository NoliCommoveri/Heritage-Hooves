- **The operator supplied nine stable names and asked for them distributed by breed fit, and confirmed volume breeders for both new breeds** (resolving §2.1's "recommended against" — the operator wanted full parity, three personalities per breed, not two). Final mapping: Quarter Horse keeps its existing personalities, renamed by migration `0136` — Fair Meadow (volume breeder) → **Apples and Oats Ranch**, Cedar Hollow (conformation specialist) → **Bronco Valley**, Willow Creek Barrels (discipline barn, Barrel Racing) → **Horseshoe Bay**. - **German Warmblood's discipline barn targets Show Jumping, not Dressage** — the spec's §2.2 left this genuinely open (both fit the breed), and this session read the operator's own chosen name for the stable, "Springen Stables" ("springen" is German for "to jump"), as resolving it in Jumping's favour rather than asking a second question when the answer was already implied. Flagged to the operator in the same turn in case that reading is wrong — cheap to fix with `UPDATE npc_policy SET target_discipline_code = 'dressage' WHERE stable_id = (SELECT id FROM stables WHERE prefix = 'Springen Stables')` if so.
- **Every new personality's numbers are its Quarter Horse counterpart's, verbatim** (spec §2.4): conformation specialists copy Bronco Valley's row, discipline barns copy Horseshoe Bay's, volume breeders copy Apples and Oats Ranch's (capacity 200, vs. 40 for the other two personalities). No new numbers were invented for this session's two breeds.

- **`src/db/reset.ts`'s NPC re-seed block was refactored into one `personalityStableStatements` helper** called nine times, rather than copy-pasting the three-INSERT shape a ninth time — the file's own comment explains why nine copies stopped being the boring option once slice 0015 also had three. This is the one real code change beyond the two migrations.
- **Six existing `*-d1.test.ts` files hardcoded a player-test-stable id that assumed exactly four NPC stables already existed** (`test/health/acquired-d1.test.ts`, `test/market/sale-d1.test.ts`, `test/market/stud-d1.test.ts`, `test/market/sell-into-offer-d1.test.ts`, `test/npc/buying-d1.test.ts`, `test/npc/pet-home-d1.test.ts`) — each seeds its own player stable by relying on SQLite's `stables.id` autoincrement continuing on from whatever the migrations left behind, rather than an explicit id. **2026-08-04 — Acquired conditions (colic, laminitis, and the rest): specified, not built.** `docs/slices/0020-acquired-conditions.md` is the new document — a full slice specification, not a lighter data record like the two entries below it, because it needs new engine code, a schema change and two tick stages, not just new rows against existing machinery.

- **Two design calls were put to the operator directly before any of this was written**, the same way slice 0010's death-window question and slice 0017's stud-fee questions were: whether an ignored acute condition should carry real death risk (**yes, decided** — colic 40% untreated vs 5% treated; only 4 of the 12 conditions carry any death branch at all), and whether laminitis/navicular should be tied to the `foot_robustness`/`joint_robustness`/`ligament_robustness` substrate slice 0014 built ahead of use, or stay purely non-genetic this pass (**tied in, decided** — four of the twelve conditions read a robustness trait as an onset modifier).
- **One engine, two phases, twelve rows** — an `onsetProbability` function (care/workload/location/feed/robustness in, a per-game-day probability out) and a `rollOutcome` function (treated-or-not in, one of resolved/manageable/degenerative/death out), never one function per condition. Mirrors slice 0010's own founding choice not to write a function per single-gene condition.
- **A new `conditions.category` value (`acquired`) and a new `severity_class` value (`acute`)** — no migration needed for either, since neither column carries a `CHECK` constraint (confirmed against `migrations/0052`). `acute` is a genuinely new *shape* of consequence, not just a new value: every prior severity class was a fixed, foreknown outcome (GBED always dies on a snapshotted date); this one is a real, still-open event that resolves into one of the other three or clears entirely, which needed naming as its own thing rather than stretched to fit.
- **Onset probability is computed per game day, not per tick**, deliberately — `1 - (1-p_day)^daysSinceLastCheck` — so a world that ticks more often than once a game day never becomes riskier by accident, the same trap `computeUpkeep` already avoids by deriving its charge from `daysOwed`.
- **Robustness modifies onset only, not outcome severity** — a structurally weaker horse gets laminitis more often, not a worse case of it once it happens. Named explicitly in the document's own §12 as a real simplification worth revisiting, not a decision to forget was made.
- **Workload, for now, is show-entry count in a trailing 90-day window** — a deliberate, named departure from slice 0013 §3.4's own reasoning that workload "needs training to mean anything." The document argues a legible partial signal now beats none, and flags itself as due for replacement once a real training system exists.
- **Laminitis reads `feed_level` directly and gives Premium feed a real downside** — richer feed measurably raises laminitis onset risk. This is a direct answer to a risk slice 0013 §13.2 flagged about itself ("premium feed... may be worth it only for a stable that is already winning") rather than a coincidence.
- **No new heritable trait was added.** Colic, ulcers, tying-up, strangles, and three others have no robustness link at all — `TRAITS` is append-only and adding a trait changes every future horse's genotype forever, judged a bigger decision than this document needed to make.
- **`horse_conditions` gains an `outcome` column, distinct from `conditions.bars_showing`** — because whether a specific horse's incident became career-ending is a fact about that one incident, not a flat property of "laminitis" the condition. Show eligibility reads the per-incident column for the acquired set; the single-gene panel's flat `bars_showing` (HERDA) is untouched and still works the old way.
- **The document flags its own bug rather than shipping it silently**: §7.1 names a marker-column naming mismatch (`last_incident_check_tick_seq` needs to hold a game-day count, not a tick count, and should be renamed `last_incident_check_game_day` before build) and deliberately leaves the earlier wrong name in the spec text so a reviewer can see the discrepancy was already caught rather than freshly discovered.
- `CLAUDE.md` §10 gained a new row pointing at the document.

**2026-08-04 — The seven non-Quarter-Horse disease panels: specified, not built.** `docs/breed-disease-panels.md` is the new document, same "data record, not a built feature" status `docs/breed-ideal-vectors.md` already carries — nothing in `conditions`, `loci`, or any `founding_allele_pool` has actually changed.

- **Only single-gene conditions are specified**, because that is the only category with working machinery (slice 0010). Colour-linked conditions (melanoma via grey, MCOA via silver) and polygenic ones (laryngeal neuropathy, DSLD, insect bite hypersensitivity, osteochondrosis) are all listed and deferred with reasons in the document's §6, not built — they need `conditions.onset_model` (deliberately not built, slice 0010 §3.2) or, for MCOA, a Silver locus that does not exist yet.
- **Six new loci recommended: `SCID`, `CA`, `LFS` (Arabian), `WFFS` (German Warmblood), `DWARF`, `HYDRO` (Friesian)** — all real, named, single-gene equine conditions with identified genes, translated onto the existing `trigger` shape the same way HYPP/PSSM1/HERDA/GBED were. **Three of the seven breeds (Thoroughbred, Paso Fino, Icelandic) get no buildable single-gene condition at all**, and Nokota gets none deliberately (overview §4a's "None distinctive," the healthy landrace) — this isn't a gap in the research, it's what real equine veterinary genetics actually looks like for those breeds, and overview §3a predicted exactly this for the Thoroughbred by name.
- **After this is seeded, the game's lethal single-gene count becomes five** (GBED existing, plus SCID/LFS/WFFS/hydrocephalus) — landing exactly on overview §3b's own stated ceiling of "four or five across the whole game."
- **Unlike the ideal-vector document, this one has no show-barn blocker.** Disease panels create no show classes and touch no NPC stocking logic, so `docs/breed-disease-panels.md`'s contents are seedable independently, any time — the document's §8 lays out the (short) migration plan.
- **One question flagged for whoever builds it rather than decided here** (document §9): the game's lethal-foal death window (`lethal_foal_death_game_days`) is a single global config value, currently 30 game days, but SCID's real death timeline is months rather than days. The document's own lean is to reuse the shared window and disclose the compression honestly in the teaching text, rather than add a per-condition override column ahead of a second condition actually needing one — but says plainly this is a call for the implementing session, per `CLAUDE.md` §2.
- `CLAUDE.md` §10's "the other seven breeds" row updated to point at both documents.

**2026-08-02 — `src/lib/rng.ts`: seeded randomness.** `makeRng(seed): Rng` gives `{ next(), int(maxExclusive), pick(items), shuffle(items), normal(mean, sd) }`. `deriveSeed(parentSeed, label)` makes a deterministic sub-seed — call this, never `makeRng` twice from the same stored seed. `randomSeed()` is the *only* place `crypto.getRandomValues` may be called, and only to mint a brand-new seed to store on a new row (horses, pregnancies, shows, …) — never to make a random decision directly. There is a golden-value test in `test/rng.test.ts` asserting exact output for `makeRng(12345)` and `deriveSeed(12345, "genotype")`. If you ever have a reason to touch the RNG algorithm itself, that test will fail — treat that failure as the whole game's stored history becoming unreproducible, not as a test to update.

**2026-08-02 — `src/lib/time.ts`: the wall clock.** `localParts(utcSeconds, timeZone)` returns `{ year, month, day, hour, minute, dateKey, minutesOfDay }` via `Intl.DateTimeFormat`. `formatLocal` for display, `parseSlot("HH:MM")` for minutes-since-midnight, `nowUtcSeconds()` for the current instant. Never compute offsets by hand. `src/tick/slot.ts`'s `decideNextSlot` is the pure function that decides which tick slot (if any) is due — it takes `SlotState` + `CurrentLocal` and returns a decision; it does not touch the database, which is what makes `test/tick-slots.test.ts` possible without one.

**2026-08-02 — `src/lib/html.ts`: the templating helper.** `` html`...` `` escapes every interpolated value by default; wrap already-safe HTML in `raw(...)` to inline it unescaped (used for nesting one `html` result inside another, and only for that). Every route in `src/render/` builds its page through `pageShell()` in `src/render/layout.ts`, which renders the game-day header, the nav, and the paused banner.

**2026-08-02 — signed-cookie sessions (`src/lib/session.ts`, `src/lib/cookies.ts`).** No sessions table, per CLAUDE.md §13. `hh_session` is `<accountId>.<issuedAt>.<hmac>`, HMAC-SHA256 over `env.SESSION_SECRET`, `HttpOnly; Secure; SameSite=Lax`, re-issued once it's a day old. `hh_stable` is the same pattern holding the selected stable id — it is a UI convenience only; every stable-scoped route (`src/routes/stables.ts`) re-reads the stable from the account_id on the row and 404s if it isn't owned by the logged-in account, never trusting the cookie alone.

**2026-08-02 — the prefix registry (`stable_prefix_history`).** Every prefix ever claimed, current or retired, is a row here, with the unique index living on `prefix`, not `stable_id`. Creating a stable and renaming one both write to this table and `stables.prefix` atomically via a single `env.DB.batch([...])` (D1 batches are one implicit transaction — any statement failing rolls the whole thing back). Creation uses SQLite's `last_insert_rowid()` inside the batch to link the new `stable_prefix_history` row to the just-inserted `stables` row, which is why `stable_id` could stay `NOT NULL` as the schema in the slice document specifies, rather than the insert-history-row-first-with-a-null-stable_id flow the document narrates — same guarantee (a taken prefix, live or retired, rejects the whole operation), true atomicity, no relaxed constraint. **2026-08-02 — `/admin/migrations`: applying migrations from the browser, no terminal.** Built directly in response to the operator hitting exactly the failure mode this exists to fix: a brand-new D1 database with no tables yet, so `/setup` (and every other page) 500'd with "Something went wrong." `src/db/migrations.ts` bundles every file in `/migrations` into the Worker as text — see the `[[rules]]` entry in `wrangler.toml`, which tells the bundler to treat `*.sql` imports as raw strings. **The glob had to be `**/*.sql`, not `migrations/*.sql`** — wrangler's rule matcher (`glob-to-regexp`, no `globstar` option) tests the *literal import specifier text* (`../../migrations/0001_world.sql`), not a resolved path, and without globstar even a single `*` compiles to `.*` — so the glob just needs `*` somewhere before `migrations/`, and `**/*.sql` is the clearest way to write that. Confirmed by actually running `wrangler dev --local` end to end (fresh DB → apply migrations → `/setup` succeeds → the route locks down to admin-only once an account exists), not just by reading the bundler source.

Each migration's SQL is split into individual statements by `src/lib/sql.ts`'s `splitSqlStatements` (strip `--` line comments, split on `;`) rather than passed to D1's `exec()`, which requires newline-separated statements and breaks on our pretty-printed multi-line `CREATE TABLE`s (see the comment in `sql.ts` and the workers-sdk issue it links). Each migration's statements plus its own tracking-row insert run through `env.DB.batch()` — the same atomic-batch pattern `createStableWithPrefix` already uses — so a migration lands completely or not at all.

The tracking table is literally `d1_migrations`, with the exact column schema and bare-filename `name` values that `wrangler d1 migrations apply` itself uses (confirmed by reading `wrangler`'s own source, since the Cloudflare docs site 403's this environment's fetch tool). This was deliberate, not incidental: it means the browser path and the CLI path (`npm run migrate:remote`) share one history and can be freely mixed, in either order, without redoing or fighting each other.

The route (`src/routes/migrations.ts`) bypasses `buildContext` entirely, the same way `/health` does, because `buildContext` loads the `world` and `config` rows and throws if those tables don't exist yet — which is exactly the state this route has to work in. Its own auth check treats "the `accounts` table doesn't exist, or has zero rows" as open-to-anyone, the same trust model `/setup` already uses (whoever gets there first is trusted, because nobody could possibly be logged in yet either way); once a first account exists, it requires a valid admin session like every other `/admin` route.

**2026-08-02 — Genetics core (slice 0002): the genotype blob, the missing-locus rule, and one deviation from a literal reading of it.** `horses.genotype` is JSON, shape `{ v: 1, mendelian: { <locus code>: [allele, allele] }, polygenic: { <trait code>: "<20 chars of 0/1>" } }` — see `src/engines/genetics/genotype.ts`. `v` is the blob's own schema version; bump it and handle both shapes if the shape ever changes, rather than migrating every horse's JSON. A **missing** locus or trait key is legal (a horse born before that gene existed) and is read via `getMendelianPair`/`getPolygenicString`, never `genotype.mendelian[code]` directly. **Every iteration over loci goes through `LOCI` in `src/engines/genetics/loci.ts`, in that array's order — never `Object.keys(...)`** — this is load-bearing for reproducibility (CLAUDE.md §5.2): the RNG draws one allele per locus in sequence. `LOCI`'s `alleles` tuple is each locus's canonical storage order (a stored pair is always sorted into it via `sortAllelePair`); its separate `wildType` field is the missing-locus default. **Those two are not always the same allele** — `§4.2` of the slice document describes the default as "the last allele in canonical order," which holds for four of the five loci, but DMRT3's canonical order is fixed by real-world convention as `["C","A"]` even though `A` is the rare (2%) gait mutation and `C` is the common wild type. Defaulting a legacy horse to `alleles[1]` would have silently made it gaited; `wildType` is spelled out per-locus instead. Flagging this because it's a literal disagreement with one sentence of the slice document, resolved in the document's own favor of intent (a missing locus must never grant a trait) rather than its literal mechanism.

Sub-seed labels in use, all via `deriveSeed` (never a second `makeRng` from a stored seed): `mendelian_sire`, `mendelian_dam`, `polygenic_sire`, `polygenic_dam`, `sex` (all derived from a foal's own `rng_seed` in `combine`/`breedNow`), and `founder_polygenic` (derived from a founding horse's own `rng_seed` in `createFoundingHorse`). `birth_noise` is reserved — not drawn anywhere yet — for whichever slice first expresses polygenic potential; see the comment in `src/engines/genetics/polygenic.ts`.

**COI uses the tabular kinship recursion, not Wright's path method** (`src/engines/genetics/pedigree.ts`'s `kinship`/`coefficientOfInbreeding`) — exact, only needs parent pointers and each ancestor's own stored `coi`. `horse_ancestors.path_count` **does not feed the COI at all**; it exists only so "this ancestor appears N times in the pedigree" can be displayed. `db/horses.ts`'s `loadPedigreeContext(env, sireId, damId)` is the two-query load behind both the breeding preview and the actual birth — one query for every ancestor id either parent has, one for those horses' `(id, sire_id, dam_id, coi)` rows — which is what guarantees the number shown before confirming a pairing is the number the foal is actually born with. Reuse it rather than writing a third way to load the same subgraph.

**Referencing a just-inserted row from several dependent inserts in the same D1 batch:** `last_insert_rowid()` (used by `createStableWithPrefix`) only stays correct for a *single* statement immediately after the insert it refers to — it goes stale the moment another insert runs. Inserting a foal needs to write a variable number of `horse_ancestors` rows all pointing at the just-inserted foal, so each one uses `(SELECT id FROM horses ORDER BY id DESC LIMIT 1)` instead — safe because a D1 batch is one transaction and nothing else can insert into `horses` in the middle of it. Reach for this pattern, not `last_insert_rowid()`, whenever more than one dependent statement needs the same freshly-minted id. (Slice 0003 update: this logic now lives in `buildFoalInsertStatements` in `src/db/horses.ts`, not `breedNow` — see the 2026-08-03 entry below. `breedNow` itself is deleted.)

**2026-08-03 — Slice 0003 (pregnancy, heat and fertility) built. `breedNow` is deleted; coverings and pregnancies are real tables; two new tick stages.** Followed `docs/slices/0003-breeding-and-fertility.md` closely; nothing in it was disagreed with. What a future session needs to know:

- **`src/engines/breeding/` is new** (`fertility.ts`, `cycle.ts`, `season.ts`, `twins.ts`) — pure functions, no DB access, same pattern as `src/engines/genetics/`. `fertility.ts`'s `fertilityPotential(horse, geneMin, geneMax)` is the one function in the whole codebase allowed to read a horse's genotype for a purpose an NPC or a viewer must never see (slice 0003 §5) — it is called from exactly one place, `src/db/coverings.ts`'s `resolveOneCovering`, and nowhere else. If you ever find yourself wanting to call it from a route or a render function, stop — that's the truth/knowledge line (CLAUDE.md §12) and you're about to cross it.
- **The fertility trait's missing-value rule is its own function, not the shared one.** `getPolygenicString` (slice 0002) reads a missing trait as all zeros, which is correct for a conformation trait and would read every horse alive before this slice as almost sterile. `fertilityPotential` checks for the key itself and falls back to `deriveSeed(horse.rng_seed, 'fertility_legacy')` instead — a stable, well-distributed stand-in per horse, never a guess. Do not call `getPolygenicString`/`potential(...)` for `'fertility'` directly anywhere; always go through `fertilityPotential`.
- **The oestrous cycle is measured in ticks (`horses.cycle_anchor_tick_seq`), never game days** — slice 0003 §2 explains why (a real 21-day cycle aliases against a 10-game-day tick). `src/engines/breeding/cycle.ts`'s `cyclePhase`/`isInSeason`/`ticksUntilNextEstrus` are the only place that arithmetic happens. Rolled once per mare, from her own seed via `deriveSeed(seed, 'cycle_slot')`, at creation (`createFoundingHorse`) or at foaling (`db/pregnancies.ts`'s `foalOnePregnancy`) — never re-rolled except at foal heat, when the tick resets a dam's own anchor to `tickSeq + 1` after she foals.
- **A covering (the mating event) and a pregnancy (one row per foal) are different tables**, per slice 0003 §6 — a covering can produce zero, one or two pregnancies (twins). Booking (`db/coverings.ts`'s `bookCovering`) is a plain insert from the breeding route. Resolution is the tick's first breeding stage, `resolveDueCoverings`: finds every booked covering whose mare is in season this tick (done in SQL — `cycle_anchor_tick_seq` is always ≤ `tickSeq`, so a plain `%` is safe), rolls conception, and on success rolls twins and writes one or two pregnancies — covering-status-update and pregnancy-inserts land in one `env.DB.batch()` together, which matters: without that atomicity, a crash between the two either strands a conceived covering with no pregnancy, or (on retry) double-creates the pregnancy, because the covering's `status` column is what makes the whole stage idempotent (CLAUDE.md §5.4).
- **Genetics are rolled at conception, stored on the pregnancy (`rolled_genotype`, `rolled_coi`), and only written into a `horses` row at foaling** (slice 0003 §3.9-§3.10) — `foal_rng_seed` is minted at conception and becomes `horses.rng_seed` unchanged. `src/db/horses.ts`'s `buildFoalInsertStatements` is what `breedNow` used to do inline; it now just writes down genetics that were already decided, and is shared by the tick's foaling stage (`db/pregnancies.ts`'s `foalDuePregnancies`). If a later slice adds a second way to create a foal (e.g. slice 0004's frozen semen), reuse this function rather than inlining another `INSERT INTO horses`.
- **Twins are two independent rolls off the covering's own seed** (`double_ovulation`, `twin_continue` — `src/engines/breeding/twins.ts`'s `rollTwins`), and when they happen, each twin gets its own freshly-minted `foal_rng_seed` and its own independent genotype and gestation-length draw — not identical twins, and not necessarily born on the same day (verified in local testing: one twin foaled 11 game days after the other). The admin "force next twins" control (`/admin/breeding`) is a one-shot `config.flags.force_next_twins` boolean, consumed by whichever covering is the *first to actually conceive* after it's set (not the first to resolve) — if conception fails, the flag stays armed for the next attempt.
- **New sub-seed labels**, all via `deriveSeed`: from `horses.rng_seed` → `cycle_slot`, `fertility_legacy`; from `coverings.rng_seed` → `conception`, `double_ovulation`, `twin_continue`; from `pregnancies.rng_seed` → `gestation`; from `pregnancies.foal_rng_seed` → the slice 0002 labels, unchanged, plus `cycle_slot` (reused for a mare foal's own cycle roll at foaling).
- **The conception estimate shown to a player is not the number rolled**, deliberately (slice 0003 §5). `db/coverings.ts`'s `estimateConceptionChance` calls the same `conceptionChance` engine function the real roll uses, but with both fertility factors fixed at `1.0` — a subfertile mare's owner finds out by missing, not by reading her genotype. Never wire the breeding screen up to `fertilityPotential` directly.
- **Migrations 0017-0021.** 0021's backfill (`cycle_anchor_tick_seq` for mares that predate this slice) uses `rng_seed % estrous_cycle_ticks` rather than the real `deriveSeed('cycle_slot')` algorithm, because a plain-SQL migration has no access to the JS RNG. Deliberate simplification, documented in the migration itself — still deterministic and evenly spread, which is all a one-time backfill needs.
- **`/admin/breeding`** (new admin subpage, in the existing admin subnav pattern) is read-only display of the live tunables plus the force-twins control — no editing form, per CLAUDE.md §13 ("no polished admin UI"). If a later slice wants these tunables editable from the browser, extend `/admin/config` rather than inventing a second config-editing UI.
- Verified end-to-end against a local `wrangler dev` + `d1 migrations apply --local`: booking, both refusal paths (out of season, recovering), conception, forced twins (two independently-gened foals, different due days), foaling, pedigree/COI/prefix on the resulting foal, the in-season barn badge, and the admin breeding page.

**2026-08-03 — the location flag: `src/engines/care/location.ts`, and why the settling period is load-bearing.** A horse is either `barn` or `pasture` (`horses.location`). At pasture it still ages, still grows, still carries every gene, and still dies of old age on the day `natural_death_game_day` says — but its care timers are frozen, it costs no board, and it cannot be bred or shown. Three things a future session should not undo without understanding them:

- **`workAvailability()` is the single implementation of "can this horse work".** Show eligibility takes it as a resolved `WorkAvailability` value rather than re-deriving it from `(location, changedDay, settleDays)`, and breeding calls the same function directly. That is deliberate: breeding is not a show and never goes through `checkEligibility`, so a copy of the rule would have been the second place it lived, and the two would have drifted the first time the settling period was retuned.
- **`horses.location_changed_game_day` does two jobs on purpose.** While the horse is out it is when the care timers stopped, so bringing it in credits `game_day - that` back onto both (`bringInFromPasture`, with a `MIN(..., game_day)` belt-and-braces cap). While the horse is in it is when the settling window started. The invariant making the credit exact is that **care calls are refused for a horse at pasture** — the route checks and `callOneHorseCare`'s own `UPDATE` re-checks with `AND location = 'barn'`. If you ever add a path that shoes a pastured horse, that credit silently over-counts.
- **The settling period (`pasture_settle_game_days`, 30) is what makes free board defensible.** Pasture costs nothing (`pasture_upkeep_multiplier`, 0 — a live tunable, raise it if board stops being a real sink). Without a wait on the way back in, the optimal play is to park every horse outside, pay nothing, and bring one in on show morning. With it, turning a horse out is a commitment to skipping the next show. Do not set it to 0 without replacing the trade-off with another one.

`timerState` gained an optional `atPasture` and a sixth `CareStatus`, `at_pasture` — optional so every pre-flag caller and test kept meaning what it meant. A pastured horse also carries **no feed delta**: feed is what is in the barn's mangers, and a horse at grass is outside that trade, so it comes out at exactly 1.00 with every component neutral. `computeUpkeep` takes `pastureHorses`/`pastureMultiplier` alongside `aliveHorses`/`feedMultiplier`, with the two groups **rounded separately then added** so a barn with nothing out is charged byte-for-byte what it was before the flag existed.

**2026-08-03 — slice 0014, all three parts (age decline, condition management, the robustness genes), and the one argument a future session most needs from it.**

- **`TRAITS` being append-only is not a style preference — it is the whole reason Part C exists as a separate, time-boxed piece of work.** `polygenic.ts`'s `TRAITS` array is the source of truth for both display order *and* the RNG draw sequence every polygenic stream reads in lockstep (`pool_polygenic`, `founder_polygenic`, the two inheritance gametes, `birth_noise`) — each draws a fixed number of values per trait, in `TRAITS`' own order, so appending a trait only ever adds draws at the *end* of every stream and never perturbs an earlier one (proved, not asserted, by `test/founding/generate.test.ts`'s "appending robustness traits changed no earlier draw" test, which pins byte-exact bit strings captured at the moment the traits were appended — capture those before editing `TRAITS`, because they cannot be recovered afterward). The cost of this discipline is that `TRAITS` reads as an odd, un-tidy list — conformation, then ability, then `fertility` (slice 0003), then `agility` (slice 0012), then the three robustness traits (slice 0014) — and that oddness is deliberate: it is what tells the next session that inserting into the middle of this list is never safe, only appending to the end. **The reason this couldn't wait for the slice that actually uses these traits:** a genotype is written once, at birth, and a missing polygenic key reads as zero-out-of-twenty (the bottom of the range) forever — `getPolygenicString`'s pad-with-zeros behaviour, which is correct for "this horse predates this trait and truly can't be measured on it" but is a *wrong answer masquerading as a real one* for a soundness trait, where zero means "maximally fragile". A horse born before the reset in slice 0014 §11 would have been permanently, incorrectly unsound the moment anything read this trait. Compare this to a **Mendelian** locus (frame overo, say): a missing locus reads as two copies of wild-type via `getMendelianPair`, which is the *correct* answer (a horse that predates the locus genuinely doesn't carry it) — that is why colour loci were safe to defer indefinitely (`docs/horse-game-overview.md` §3b, corrected this session) and polygenic traits were not.

**2026-08-03 — `docs/analysis/` added, and slice 0018 specified: why selective breeding currently stops working after about two real years.** No game code changed; this entry records a new directory, a new tool, and a measurement a future session should not have to redo.

- **`docs/analysis/` is a new directory `CLAUDE.md` §4's layout does not list.** It holds analysis tools that reason *about* the game without being part of it. The first inhabitant is `population-sim.mjs`, a standalone Node script (`node docs/analysis/population-sim.mjs`, no dependencies, no build step) that runs the live conformation and showing formulas over a simulated closed population. **It is deliberately not in `test/`** — `vitest run` only collects `*.test.ts`, so a `.mjs` there would be dead weight that looks like a test; and deliberately not in `src/`, where it could break a deploy the operator cannot fix. Nothing imports it and nothing depends on it.
- **It keeps its own copy of the game's constants and its own PRNG, on purpose, and that copy can drift.** The header names the source migration or engine beside every constant. `CLAUDE.md` §5.2's "no `Math.random()`, ever" is about the *game* being reproducible from stored seeds; this file is seeded too, but keeps no dependency on `src/lib/rng` so that it cannot be broken by a change to it. The trade is real: **if you retune `conformation_noise_sd`, `inbreeding_depression_factor`, `show_ideal_falloff`, `show_noise_sd`, or the QH ideal vector, update the CONSTANTS block or delete the file.** A drifted simulation is worse than none.
- **What it measured, at migration 0098.** Five stables, six mares and two stallions each, truncation selection on show score, same-stable breeding as `routes/horses.ts:415` enforces today: mean show score climbs 65.7 → ~84 by generation 15 and then **stays there through generation 50**, with COI settling around 60%. On the real clock (30 game days per real day, ~4 game years per generation) that plateau lands about **two real years** into play.
- **The three findings worth carrying forward even if slice 0018 is never built as written:**
  1. **Reliability is a packaging problem, not a merit problem.** Two parents whose potential sits exactly on the QH ideal produce foals averaging 81.6 with 10% reaching a score of 90 when their alleles are packaged heterozygously — and 89.6 with 50% reaching 90 when packaged homozygously. Same merit, five times the hit rate. Nothing on any screen shows a player zygosity, and the inbreeding penalty punishes the only route to it.
  2. **`realization = 1 − COI × factor` is a tax selection routes around, not a brake.** Because it shrinks expression toward the anchor of 50, players answer it by selecting more extreme genotypes — until they run out. At COI 60% a correct QH shoulder (target 70) requires 20 alleles of 20, the maximum in the game. That ceiling, not selection pressure, is what stops the curve.
  3. **Stored COI understates true homozygosity in a long-closed pool**, because `PEDIGREE_DEPTH` = 6 treats deeper ancestors as unrelated founders. This is the right trade for the reasons `loci.ts` gives, but it means a population can be far more fixed than its COI column admits, and finding (1) is invisible on every screen we have.
- **Selection accuracy is not the bottleneck, and a future session should not start there.** Measured: r(own show score, true genetic merit) = 0.74; a twenty-foal progeny test reaches only 0.80. An estimated-breeding-value system is the obvious first idea and buys very little. Recorded so it is rediscovered as *rejected* rather than as new.
- **`docs/slices/0018-genetic-progress-and-inbreeding.md` is filed as a spec with seven open questions in its §10, and `CLAUDE.md` §10 now carries a "specified, not built" row pointing at it.** The largest of those questions — how hard the replacement fitness penalties should bite, and whether a foal lost to inbreeding is acceptable for these players — are `CLAUDE.md` §2 "stop and ask" material. **Do not build Part A's conformation change on its own**: dropping `inbreeding_depression_factor` without the fitness penalties that replace it makes inbreeding strictly free, which is worse than today. Note also that this factor is read fresh on every page view, so changing it re-scores every inbred horse in the game the moment it deploys.

**2026-08-03 — `docs/analysis/stable-timeline.mjs` added, and slice 0019 specified: how long a child actually waits before a breed feels won.** No game code changed. Companion entry to the slice-0018 one above; read that one first for why `docs/analysis/` exists and how its copied constants can drift.

- **The second analysis tool answers a different question from the first.** `population-sim.mjs` asks "does the population improve at all?" (it plateaus). `stable-timeline.mjs` asks "how long until one child has six good horses?", simulating a single stable at tick resolution — real oestrous cycles, conception rolls, gestation, ageing and death, the four QH disease loci at their seeded frequencies, GBED foals lost, affected horses excluded from breeding, carrier × carrier vetoed, and capacity culling on what the player can *see* rather than on the truth. It carries `missRate` and `colourDistraction` knobs standing in for a real child: heats missed because nobody logged in, and pairings chosen for a pretty foal.
- **Measured, for a casual child (45% of heats missed, 35% of pairings colour-driven), at gestation 60:** six horses whose conformation genes score ≥90 takes a median of **1.2 real years**, and **a third of children never get there** — 19 lines in 200 died out entirely, 48 more were alive but stuck at COI ~45%. The discipline line is worse: six horses that dominate the NPC barrel field takes **1.8 years**.
- **The cause is that founding stock is a coin flip.** Every polygenic allele is drawn at `quality_bands.mid` = 0.50, so on the Quarter Horse's ideal (11/14/7/10 of 20) **the shoulder is four alleles short on every founding horse in the game**, and most of a child's first year goes into closing a gap that is the same gap for every child, every breed, every time. The alleles are already in the pool — it is a frequency shift, not a search. **Speeding the clock up does not help**: the operator's gestation change from 340 to 60 game days made everything ~30% faster and moved the failure rate by one run in two hundred.
- **Two findings a future session should not have to re-derive:**
  1. **Conformation and ability are on different scales, and must not share a success bar.** Conformation targets are *intermediate*, so a mid-band founder already scores ~78 of 100. Ability traits are `higher_better` with anchor 0 and no target at all (`TRAIT_DIRECTION`, and `scoreAbilityEntry` is a plain weighted mean), so a mid-band founder scores ~50 of 99. Reaching "90% of perfect" in a discipline was **0 of 200 runs**. That is fine and not a bug — the NPC show barn is stocked at the *same* mid band, so ~50 is the field, and discipline success means winning rather than approaching perfection.
  2. **`jump_scope` has weight 0.0 in Barrel Racing, the only seeded discipline**, and `stamina` has 0.2. Anything that hands a horse a "special" ability trait must draw only from traits some *enabled* discipline actually weights, or it will hand children horses whose one special quality cannot be scored anywhere. Today that pool is agility, speed and trainability.
- **`docs/slices/0019-founding-specialists.md` is filed as a spec**, and `CLAUDE.md` §10 carries a "specified, not built" row. It gives every founding horse one conformation trait near its breed's target and one ability trait high-with-headroom, and doubles the consignment rate; measured together that is ~200 days and a 3% failure rate on both lines. **Specialists and consignment flow do different jobs and neither works alone** — specialists fix speed, the outcross flow fixes the failure rate.
- **Two traps recorded in that slice's §7, worth repeating here because both are silent.** (1) **Do not make the specialist trait homozygous.** It is the obvious way to make a trait breed true, and slice 0018 §1.1 measures homozygosity as *the* long-term reward — handing it out in the founding grant spends it on the first five minutes. (2) **Do not skip the existing `pool_polygenic` draws for the specialist trait.** That loop draws 20 alleles per trait off one stream; skipping any of them shifts every trait after it and the same stored seed stops producing the same horse. Let the existing loop run untouched and *overwrite* the specialist trait afterwards from a separate stream with a fresh label — the same generate-then-overwrite pattern `applyConsignmentInjection` already uses.
- **The blocker on the operator's "eight breeds" goal is data, not code:** the conformation half of slice 0019 does nothing for a breed with no `ideal_vector`, and **seven of the eight breeds have none seeded**. `docs/breed-ideal-vectors.md` has all eight drafted; turning it into a migration is the prerequisite.

Four things a future session working anywhere near loci or traits should know, independent of whether this slice is ever built:

- **D1 is SQLite: `json_set`, not `jsonb_set`, and no `::jsonb` cast.** Both drafts were Postgres and would have failed at `/admin/migrations` — an error the operator cannot debug. The pattern that works, and that preserves an already-seeded JSON column rather than retyping it: `UPDATE breeds SET ideal_vector = json_set(ideal_vector, '$.traits.head_profile', json('{"target":35,"weight":0.8}')) WHERE code = 'QH';`. The `json()` wrapper is what makes SQLite store an object rather than a quoted string — without it the column silently gains a string where every reader expects an object.
- **Adding a locus to `LOCI` breaks every breed until the founding pools are re-seeded in the same push.** `parseAllelePool` (`src/engines/founding/pool.ts:17`) iterates every locus in `LOCI` and throws on a missing key, so founding stock, the consignment dealer, admin horse creation and `/admin/breeds` enabling all fail together. - **The consistency tests hardcode migration filenames.** `test/genetics/consistency.test.ts` parses a fixed list (`0015` + `0050` for loci; `0029` + `0061` + `0081` for traits) and asserts exact agreement with `LOCI`/`TRAITS`. A trait added to a breed's `ideal_vector` without being added to `TRAITS` is silently ignored — no error, no score change, nothing to see. Conversely `judges.trait_weights` defaults a missing trait to 1.0, so a new conformation trait quietly changes every seeded judge's character unless their weights are set deliberately.

**2026-08-04 — NPC stables have income again: an income floor and the pet home.** New files `src/db/npcFinance.ts`, `src/db/petHome.ts` and `src/db/horseRemoval.ts`; migrations `0126`-`0128`. Specified in conversation, not a slice document.

Numbered `0126`-`0128` rather than `0118`-`0120` as first written: slice 0020 landed on `main` while this branch was open and took `0118` (the consignment change) and `0122`-`0125`. These three were renumbered to sit after all of it before merging, which was safe only because none of them had been applied anywhere yet — the forward-only rule (CLAUDE.md §8) bites the moment one has. Checked at the same time, and worth repeating as the routine for this situation: slice 0020 adds no table referencing `horses` and no `ALTER TABLE ledger`, so `deletableHorseSql`'s list below is still complete and `0128`'s ledger rebuild still copies the right columns.

Background, because the reasoning is the whole point: NPC stables only show when a player enters the same class, and only take the slots the players left (`judgeOneClass`'s never-top-up-an-empty-field rule, unchanged and still correct). That makes prize money — the game's only recurring money faucet — a function of how much the children happen to show, which is exactly the variable nobody can control. Their outgoings are real and did not change: they buy player horses on both routes in `npcBuying.ts` and pay `genotype_panel_cost` (700) every time they list. A quiet fortnight earned them nothing, so they stopped buying and stopped listing, and the market was dead exactly when the children came back to it. All three NPC stables were seeded at a balance of 0 (`0085`, and `0086` zeroed Fair Meadow) and had never been given a way to earn reliably.

- **Slice 0015 §2.5 is the precedent this follows, on the other side of the ledger.** That decision exempted NPC stables from board because "nobody is playing the stable, so the charge models no decision." The symmetric conclusion is that NPC *income* should also be a tunable rather than a simulation. Read that section before changing anything here — a future session that reintroduces NPC upkeep without revisiting this will break both halves at once.
- **Two mechanisms, and they are not interchangeable.** The income floor (`runNpcBalanceFloor`, `npc_policy.balance_floor`) is a *safety net*: once every `npc_balance_floor_interval_game_days` (360, a game year) a stable below its floor is topped back up to it, and a stable that is earning gets nothing. The pet home is the *income*. **If /admin/npc shows a stable's balance parked at its floor, that stable is living on charity and something upstream is wrong** (bad breeding, or `pet_home_payout_fraction` set too low); the two floor columns exist to make that visible.
- **The floor's marker advances whether or not any money moved, and this is load-bearing.** If `last_floor_topup_game_day` only advanced on an actual top-up, a healthy stable would stay permanently "due" and be restored the instant it dipped one unit below its floor — turning the floor into unlimited money for the buying routes. `test/npc/pet-home-d1.test.ts`'s "does not refill a stable that spends its floor away before the interval is up" pins this; do not "simplify" the marker update back inside the `if`.
- **A NULL marker means "never topped up" and reads as immediately due**, which is what gives the three existing zero-balance stables an opening balance on the first tick after `0126` lands — deliberately instead of a backfill migration.

**The pet home (`src/db/petHome.ts`) is one mechanic with two entry points, and the operator asked explicitly for it to stay that way** — same price, same ledger kind, same rule about whether the row survives.

- **The two ways in are deliberately asymmetric, and a future session must not "tidy" that.** A player's horse goes to a pet home *only* when that player clicks through `/horses/:id/pet-home` — there is no tick stage, timer or automatic path that can send a child's horse away, and a player's listing expiring still returns the horse to the barn exactly as before. An NPC stable's horse goes *only* by its listing running the full window unsold; an NPC never "decides" to use a pet home. The tick stage enforces its half structurally (it joins `npc_policy` and filters `is_npc = 1`); the player's half is enforced by there being no caller of `sellHorseToPetHome` except the route. The file header says this in as many words.
- **Price: `pet_home_payout_fraction`, 0.4 of appraised value, floored at `market_min_value`.** One number for both sides. It is meant to be a bad deal — a pet home has to be worse than selling to a player or nobody would ever use the market. No commission: commission is what the market charges for finding a buyer, and this is exactly the case where it found none. **Worth flagging for the first retune:** the operator's target payout was 600-950, but against the appraisal band `/admin/config` documents (an average adult horse 800-1,500) 0.4 yields 320-600. Either the fraction wants raising to ~0.6 or the appraisal band has drifted upward in play — check a real horse's guide value on the market before changing anything.
- **Its own ledger kind, `pet_home_payout` (`0128`), not `sale`.** So the ledger distinguishes a child buying a horse from the world beyond the five of them taking one. `getSeasonTradeSummary` counts it toward /admin/npc's earned-selling column all the same, since it is still money earned by producing a horse worth something. The Money page's `KIND_LABELS` is a `Record<LedgerKind, string>`, so `tsc` catches a missing label — that is why every new kind must be added there too.
- **The tick stage runs immediately before `expireListings` and never after it.** That ordering is what lets the split work with no change at all to `src/db/listings.ts`: the pet home claims the NPC listings that timed out with a live horse, `expireListings` closes everything left. Reversed, `expireListings` closes them first and the pet home finds nothing.
- **It excludes the Consignment Yard by joining `npc_policy`,** not by naming the prefix. The dealer mints stock out of nothing and nothing reads its balance, so paying it would print money into a stable with no use for it — and it already has its own cleanup path (`releaseExpiredConsignments`).

**Whether a departing horse's row survives is `src/db/horseRemoval.ts`'s rule, shared by both entry points.** The operator's rule: **a horse that never showed and never conceived is deleted outright; anything else is marked `removed` and kept.**

- **"Bred" means pregnant, not covered** — the operator's own clarification, and it changes real behaviour. A mare covered who never caught, or a stallion whose covering never took, *is* deletable. That is why `coverings` is absent from the eligibility list and present in the delete list instead.
- **The consequence of that, named because it is the one genuinely lossy part:** a covering names a mare *and* a stallion, so deleting a horse with a failed covering also removes the counterpart's record of that attempt. It cannot be kept for one side only, and a covering with no pregnancy behind it is precisely what the operator judged not worth keeping.
- **`deletableHorseSql` is doing two jobs at once, which is why it is longer than the phrase suggests.** It is the operator's rule *and* the proof that the `DELETE` cannot break a foreign key: every one of the fourteen tables with a `REFERENCES horses (id)` column is either named in the eligibility check (so the horse is kept) or cleaned up by `buildDeleteHorseStatements` (so the reference goes with it). **A future migration adding a fifteenth must put it in one list or the other**, or the delete starts throwing inside the tick batch. This was not theoretical — the first draft omitted `coverings` and `pregnancies.foal_id` and failed against a real SQLite with `PRAGMA foreign_keys = ON`.
- **The two stud clauses are deliberately stricter than the operator's rule.** A stud booking is a cross-stable transaction with a player's money in it, and deleting a horse in one would delete the covering underneath it, emptying the record of what a child actually paid for. So a horse that ever stood at stud or was booked to one is kept whole even with no pregnancy. It also happens to make the covering delete safe: a booking names both its horses, so no covering a `stud_booking` points at can belong to a deletable horse.
- **`pregnancies.foal_id` is set to NULL rather than the pregnancy being deleted.** Most of what gets cleared is an NPC's own home-bred surplus, so a pregnancy usually points at it — but that pregnancy is its *dam's* history, which the rule is not about. NULL is already an ordinary value in that column, and the row keeps its status, dates and both parents, so the record that she foaled survives.
- **Nothing touches `ledger`** (append-only, CLAUDE.md §7). Receipts carry the horse's name as text so they stay readable; only the `reference_id` pointer is lost. For a *deleted* horse the receipt deliberately references the stable rather than the listing, because listing ids are rowids SQLite can hand out again — a dangling pointer would eventually name somebody else's listing.
- **`endedDescription` (`src/render/horses.ts`) had to learn `end_reason`.** A pet-home horse is `removed` too, so without that check every one would have claimed it was "Retired away" on the past-horses list.
- **A broke NPC stable now goes dark instead of lowballing.** `refreshOneOffer`'s `maxPrice` floors at `market_min_value` (50), so a stable at 0 used to advertise 50 for a horse worth a thousand — which reads to a child as a broken game, not a bad deal. Both buying routes now gate on `npc_buy_offer_min_balance` (500) from one config key, so they can never disagree about whether a stable is solvent. `test/npc/buying-d1.test.ts` had a test asserting the *old* behaviour; it is now inverted and carries a comment saying so.
- **`balance_floor` is passed explicitly by every `npc_policy` insert, never left to the column's `DEFAULT 0`.** `src/db/reset.ts`'s three recreated stables mirror `0126`'s values and `foundNpcStable` takes it as a required parameter with a field on the /admin/npc form. This matters more than it looks: slice 0021's Part G world reset has not been run yet and very likely will be, and a reset that recreated every NPC stable with the floor silently off would not surface until the market stopped moving weeks later.
- **The numbers are all guesses** — floors of 5000/5000/3000 by personality, a 360-day interval, a 0.4 pet-home fraction, a 500 buying minimum. The floor can create at most one floor per stable per game year (about 12 real days at three ticks a day), small next to what player upkeep drains over the same period. Prefer retuning the fraction over shortening the floor interval — the interval is the one number that raises the ceiling on money created from nothing.
- Verified: `npm test` (69 files, 632 tests — 22 new in `test/npc/pet-home-d1.test.ts`, 1 inverted in `buying-d1.test.ts`) and `npx tsc --noEmit` both clean, including all three new migrations applying to a real SQLite database alongside every prior one, and the seeded values read back and confirmed (`pet_home_payout_fraction` 0.4, floors 5000/5000/3000, the old clearance key gone, the widened `ledger.kind` CHECK accepting `pet_home_payout`). **Not** verified against a live `wrangler dev` or real D1, and **not** verified visually — the new confirmation page and the horse page's new link have not been looked at in a browser. **Nothing here has been watched in play**: no NPC stable has run a game year with a floor, and no horse has yet gone to a pet home.
